A · Concept What is a headless CMS?

A content store with no opinion
about how that content is rendered.

A traditional CMS like WordPress ships finished HTML pages. A headless CMS exposes content over an API — REST or GraphQL — and leaves rendering entirely to whatever consumes it. The "head," the presentation layer, is missing by design.

Etymology The term came from web devs in the mid-2010s who got tired of stuffing mobile-app content into WordPress. The "head" is the rendered output. Cut it off, and what remains is a content API.
A · Architecture One backend, many heads

One body, many heads.

The backend stays the same. What changes is who's reading the API.

B · Comparison Traditional vs. Headless

The split, in a sentence.

Traditional / Coupled

WordPress renders the page for you.
  • Backend and frontend in one PHP runtime
  • Theme system controls how content looks
  • Plugin ecosystem (60k+) does the heavy lifting
  • One content type per site, one site per stack
  • Editor has WYSIWYG with live preview

Headless / Decoupled

Strapi serves JSON. You render it.
  • Backend serves data over REST or GraphQL
  • Frontend is whatever you want — React, mobile, kiosk
  • Smaller plugin ecosystem, bigger framework freedom
  • One backend can feed many frontends
  • Editor preview varies by vendor — improving fast
B · Trade-offs When headless is the wrong tool

Headless isn't better. It's different.

A small-business brochure site that the owner updates once a month is almost always better served by WordPress, Squarespace, or Webflow. Lead with this — students leave most CMS lectures thinking headless is universally superior. It isn't.

Avoid headless when…

  • The content team is non-technical and edits in-page WYSIWYG
  • The site is one website, not a multi-channel system
  • There's no frontend developer on the team
  • You need it shipped this week with a $0 budget
  • Existing WordPress is fine and the migration would be theater

Reach for headless when…

  • You're delivering content to web + mobile + something else
  • Performance is critical and you need static + CDN
  • Content structure is genuinely complex (i18n, deep relations)
  • Your team has frontend engineers who'd rather not touch PHP
  • You're replacing a creaking WordPress whose theme is unmaintainable

D · Takeaways How to read CMS statistics

So how do analysts actually measure headless?

  • Vendor revenueContentful, Sanity, Strapi report ARR. Useful for sizing the market, useless for share-of-sites.
  • GitHub signalStars, npm downloads, contributor counts. Reveals developer interest but not production deployments.
  • Developer surveysStack Overflow, State of JS, G2. Reveals what people say they use.
  • Selective fingerprintingSome tools detect specific Sanity/Contentful client SDKs in the JS bundle. Catches a fraction of real usage.
The lesson A market-share number for headless CMS is always a model, not a measurement. When you read "X% of websites use Y," the first question is: how did they count?

E · Recommendation The classroom pick

For learning, the answer is Strapi.

This isn't "Strapi is best in absolute terms." It's "Strapi is best for teaching the headless concept in 90 minutes." Five reasons:

  • No accounts, no credit cardsnpx create-strapi-app — runs locally on SQLite. Crucial in a classroom of 20+ students.
  • Open source, fully readableStudents can clone the repo, read the source, inspect the database. Pedagogically transparent.
  • REST + GraphQL out of the boxBoth API styles for free. Sanity would force GROQ on top of "headless" — two new things at once.
  • Admin UI is genuinely usableEditor concepts (content types, relations, draft/publish) come through clearly without writing schemas in code first.
  • Industry-relevantTop 3 most-used headless CMSs and the most-used self-hosted option. The skill transfers.
Honest caveat In a real product team, Sanity or Payload is often the better technical choice — particularly if the frontend is Next.js. Don't leave the room thinking Strapi is universally optimal.

F · Lab What we're building

Lab: a blog, the headless way.

A Strapi backend serves articles over REST. A Vite + React SPA fetches them and renders a list and a detail view. ~90 minutes.

Why Vite + React, not Next.js?

To isolate the headless concepts from SSR / Server Components / server actions. Students see a clean SPA fetching JSON. The mental model — backend serves data, frontend renders it — stays uncluttered. SSR is a separate lecture.

What you'll have built by the end

  • A Strapi instance running on localhost:1337 with an Article content type
  • Three published articles, editable via the admin UI
  • A Vite + React SPA on localhost:5173 rendering the articles as a clean list
  • A clear demo of why CORS exists
F · Lab — Part 1 (35 min) Stand up the backend

Step 1 — Strapi.

One command. The --quickstart flag uses SQLite so there's no database to install separately.

# Scaffold Strapi (uses SQLite, skips Cloud signup) npx create-strapi@latest blog-cms --quickstart --skip-cloud # Strapi opens http://localhost:1337/admin # Create your first admin user

Then in the admin panel

  1. 01. Create a Content Type called Article with fields: title (Text), slug (UID, attached to title), body (Long text), excerpt (Text)
  2. 02. Save → Strapi auto-restarts with the new schema
  3. 03. Create three sample articles → Publish each
  4. 04. Critical: Settings → Roles → Public → enable find and findOne on Article. This is the moment the API becomes reachable from outside.
  5. 05. Visit http://localhost:1337/api/articles → you should see JSON
F · Lab — Part 2 (30 min) Wire up the frontend

Step 2 — Vite + React.

# From your projects folder npm create vite@latest blog-frontend -- --template react cd blog-frontend npm install npm run dev # → http://localhost:5173
# .env — Vite exposes only VITE_* vars to the client VITE_STRAPI_URL=http://localhost:1337 # Use import.meta.env.VITE_* (process.env.* won't work in Vite) # Restart the dev server after editing .env
import { useEffect, useState } from "react"; const STRAPI = import.meta.env.VITE_STRAPI_URL; export default function App() { const [articles, setArticles] = useState([]); const [error, setError] = useState(null); useEffect(() => { fetch(`${STRAPI}/api/articles`) .then((r) => r.ok ? r.json() : Promise.reject(r.status)) .then((json) => setArticles(json.data)) .catch((e) => setError(`Strapi error: ${e}`)); }, []); if (error) return <p>{error}</p>; return ( <main> <h1>Course Notes</h1> {articles.map((a) => ( <article key={a.documentId}> <h2>{a.title}</h2> <p>{a.excerpt}</p> </article> ))} </main> ); }
Watch for old tutorials Strapi 5 flattened the API response. If you Google "Strapi React fetch" you'll see code with a.attributes.title — that's v4 syntax and won't work here. In v5, fields are at the top level: a.title. The documentId is the new stable key.
F · Lab — Part 3 (10 min, optional) Stretch tasks & what to look for

If they finish early.

Stretch tasks (pick one)

  • Sort newest first. Append ?sort=publishedAt:desc to the fetch URL. Add a new article in Strapi — watch it appear at the top. Server-side sorting via URL.
  • Add a cover image. Add a cover media field. Fetch with ?populate=cover (relations don't auto-populate in v5). Render with {`${STRAPI}${a.cover.url}`}.
  • Add an Author relation. Create an Author content type, add a relation from Article. Don't forget to enable find/findOne on Author too. Fetch with ?populate=author.

What to assess

  • Do they understand the boundary? Test: "What happens if Strapi goes down?"
  • Did they remember Public role permissions, or debug a 403?
  • Did they recognize the v4 vs v5 syntax issue when copy-pasting old tutorials?
  • Can they name one task harder with this stack vs. WordPress, and one easier?
